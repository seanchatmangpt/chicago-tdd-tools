# Tutorial: Author a Workflow Contract as Turtle, Validate It, and Lower It to POWL

> Diataxis axis: **Tutorial** (learning-oriented). Everything here runs against
> landed code; every API named is real and cited.

## What you will learn

Author a deal workflow as a Turtle (.ttl) contract, validate it against SHACL
shapes via `AshGraphLaw.Capability.Shacl.run/2`, apply N3 inference rules, and
lower the workflow to a POWL process model with
`PowlModel::from_powl_file`. The worked example is the landed
`examples/merger_matrix` fixture family in this repository
(/Users/sac/chicago-tdd-tools/examples/merger_matrix/).

## Prerequisites

- The `ash_graphlaw` checkout at /Users/sac/ash_graphlaw
  (a `capability` module set GENERATED by ggen from the GraphLaw capability

## Step 1: Author the .ttl contract

A workflow contract is a Turtle graph: a shapes graph (structure), a data
graph (facts), and optional N3 rule files (derived facts). The merger matrix
fixture ships all three kinds:

- `examples/merger_matrix/shapes/merger-core.shacl.ttl` — closed deal-entity
  topology. Every `sh:NodeShape` is `sh:closed true`, so any predicate outside
  the enumerated `sh:property` list fails validation (fail-closed membrane).
- `examples/merger_matrix/shapes/deal-terms.shacl.ttl`,
  `party.shacl.ttl`, `materiality.shacl.ttl` — term, party, and
  material-adverse-effect shapes.
- `examples/merger_matrix/contracts/merger-agreement.ttl` — the data graph.
- `examples/merger_matrix/rules/*.n3` — three N3 rule files.

Key structural facts of `merger-core.shacl.ttl` (real predicates, not
paraphrase):

```turtle
ex:AcmeCorpShape a sh:NodeShape ;
    sh:targetClass ex:Acquirer ;
    sh:closed true ;
    sh:property [
        sh:path ex:legalName ;
        sh:datatype xsd:string ; sh:minCount 1 ; sh:maxCount 1 ;
    ] , [
        sh:path ex:hasSubsidiary ;
        sh:class ex:AcquisitionVehicle ; sh:minCount 1 ;
    ] .
```

Note the `sh:closed true` discipline: the shape graph does not merely check
that required triples exist; it refuses predicates it did not enumerate. That
is the membrane in the POWL phase-1 net: `a01_shacl_ingest` is the root
sequence head.

## Step 2: SHACL-validate via AshGraphLaw

The SHACL capability is a generated module:
`/Users/sac/ash_graphlaw/lib/ash_graphlaw/capability/shacl.ex`. Its `run/2`
at line 142:

```elixir
@spec run(AshGraphLaw.Capability.args(), keyword()) :: {:ok, t()} | {:error, Refusal.t()}
def run(args, opts \\ [])
```

Request fields (from the same module's `@request_fields`, registry order 7,
wire op `"shacl"`):

| field | type | required |
|---|---|---|
| `data` | data_spec — `{text, dialect?, hint?, base?}` object; dialect sniffed when omitted | yes |
| `shapes` | string — SHACL shapes graph as Turtle text | yes |
| `base` | string — base IRI | no |

Refusal on unknown keys, missing required fields, or type mismatch is
`:invalid_capability_request`; a non-map engine response decodes to
`:capability_response_undecodable`. Success decodes to
`AshGraphLaw.Result.Shacl` with fields `conforms` (boolean) and `results`
(list of `{focus, path, value, severity, component, shape, message}`).

A minimal call for the landed fixture:

```elixir
{:ok, data} = File.read("examples/merger_matrix/contracts/merger-agreement.ttl")
{:ok, shapes} = File.read("examples/merger_matrix/shapes/merger-core.shacl.ttl")

case AshGraphLaw.Capability.Shacl.run(data: {:text, data}, shapes: shapes) do
  {:ok, %{conforms: true}} -> :ok
  {:ok, %{conforms: false, results: results}} -> {:refused, results}
  {:error, refusal} -> {:refused, refusal}
  # exhaustive: AshGraphLaw.Result.Shacl models only :conforms and :results;
  # run/2 returns {:ok, t()} | {:error, Refusal.t()} (capability/shacl.ex:135-137)
end
```

Divergence note: the exact shape of the `data` value depends on the
`data_spec` coercion rules in
`/Users/sac/ash_graphlaw/lib/ash_graphlaw/capability/coerce.ex`; consult that
module for the accepted forms. The `{:text, data}` form above is
illustrative; the registry metadata is the authority.

## Step 3: N3 rules

`AshGraphLaw.Capability.N3` (same generated pattern, wire op `"n3"`) carries
the rule file against the data graph. The landed rule
`examples/merger_matrix/rules/vote-threshold.n3` derives
`ex:votesCast`, `ex:yesShare`, `ex:VotePassed`, and — via cwm/EYE scoped
negation-as-failure (`log:notImplies`) — `ex:VoteFailed`:

```n3
{ ?vote a ex:ShareholderVote ; ex:votesCast ?cast ; ex:votesFor ?f .
  ( 100.0 ?f ) math:product ?num .
  ( ?num ?cast ) math:quotient ?share .
} => { ?vote ex:yesShare ?share . } .
```

The fixture vote is 700,000 of 1,000,000 cast for => 70% >= the 66.67%
threshold => PASS. This derived fact is exactly what the POWL phase nets
consume as activity coordinates.

## Step 4: Lower the workflow to POWL

The POWL compact DSL lives in `src/conformance/loader.rs`. Load a `.powl`
file with:

```rust
use chicago_tdd_tools::conformance::loader::PowlModel;

let model = PowlModel::from_powl_file("examples/merger_matrix/models/phase1_intake.powl")?;
assert_eq!(model.node_count(), 34); // under MAX_POWL_NODES = 64
```

`from_powl_file` (loader.rs, Public API section) is the module's single
declared IO boundary; unreadable files refuse with `ConformanceError::Io`.
Oversized models refuse with `ConformanceError::ModelTooLarge` when the tree
exceeds `MAX_POWL_NODES = 64` (loader.rs:47). The phase-1 net is 34/64.

The landed phase net
`examples/merger_matrix/models/phase1_intake.powl` encodes the legal workflow
as structure. The grammar (full EBNF in [03-reference.md](03-reference.md)) in
one line: `activity name = source.event` declarations, then one root block of
`sequence` / `xor` / `parallel` / `loop{...}redo{...}max N` / `silent` /
activity name.

In `phase1_intake.powl` the workflow law is structural:

- `a01_shacl_ingest` is the head of the root `sequence` — the SHACL membrane
  gates everything downstream.
- `xor { a03_covenant_conflicts silent }` — defeasible covenant conflict:
  conflict score at bottom clears silently, otherwise escalation.
- `loop { a05_cet1_buffers } redo { silent } max 3` — bounded re-buffering
  toward the CET1 >= 12.5% invariant.
- `loop { a09_intercompany } redo { silent } max 255` — AP/AR enumeration
  across 4,200 subsidiaries, bounded.
- A final `parallel { court_n01 ... court_n17 }` — courts run concurrently
  only after the linear pipeline.

## Step 5: Conformance replay

`PowlModel` is the parse gate, not the end. The lowering path is
`PowlModel` -> validated `PetriNet` (`src/conformance/validate.rs`) ->
`ConformanceSession` replay -> `ConformanceReport`
(`src/conformance/report.rs`; conforming means final marking of exactly one
token in the terminal activity and zero deviations,
`ConformanceReport::is_conforming`).

## Troubleshooting

- `ConformanceError::UnknownActivity` — referenced a name with no `activity`
  declaration; declarations must precede the root.
- `ConformanceError::ModelTooLarge` — you exceeded 64 nodes; split the net,
  do not raise the cap (the master.powl header records cap relaxation as
  PROHIBITED for the merger composition).
- SHACL `conforms: false` — read `results`; the merger membrane is
  fail-closed by `sh:closed true`.
