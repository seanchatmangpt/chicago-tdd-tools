# Epic: MCP Testing Infrastructure (v26.6.31)

**Epic key:** CHIC-310  
**Sprint:** v26.6.31  
**Status:** Planning  
**Owner:** TBD  
**Affects crates:** new `crates/chicago-mcp` crate (isolated); root workspace `Cargo.toml`

---

## Background

`osx-clnr` (codename Pentecost) ships an MCP server in `src/mcp/`. Testing it today requires either:

1. A live LLM host that speaks the Model Context Protocol, or  
2. Manual stdio piping: `echo '{"jsonrpc":"2.0",...}' | cargo run -- mcp` and eyeballing the output.

Both are unacceptable under Chicago TDD conventions. Option 1 introduces a non-deterministic external dependency. Option 2 produces no machine-verifiable artifact.

The MCP specification is a well-defined JSON-RPC 2.0 profile. The wire format is fully deterministic: initialization handshake, capability negotiation, tool-list enumeration, tool-call request/response, and error envelopes. None of those shapes require an LLM — they require a correct codec and a state machine that obeys the MCP lifecycle.

`chicago-tdd-tools` already contains all the building blocks: `proptest`, `insta`, `blake3`, `wasm4pm-compat` OCEL 2.0, `testcontainers`, and a type-level AAA state machine in `src/core/`.

This epic adds a first-class, LLM-free MCP testing module to `chicago-tdd-tools` so that any project with an MCP server (or client) can write deterministic, hermetic, sub-30 s integration tests against it.

**Reference implementation:** `~/osx-clnr` is the MCP server under test throughout this epic.

## Architectural Decision: `crates/chicago-mcp` isolation crate

**Decision (recorded):** `rmcp 2.0.0` (crates.io) is adopted as the canonical MCP type and transport layer. It lives in exactly one place in the monorepo: a new crate `crates/chicago-mcp`.

**Rationale:**

- `rmcp` pulls `tokio`, `serde_json`, `tower`, and other heavy-weight deps. Regular consumers of `chicago-tdd-tools` (`chicago-tdd-lsp`, proc-macro crates, etc.) must not pay that compile cost.
- Containing `rmcp` to one crate gives a single upgrade point when `rmcp` cuts a new major version.
- `crates/chicago-mcp` is **not** a member of the default workspace build. It is opt-in: consumers add it as `chicago-mcp = { path = "crates/chicago-mcp", features = ["testing"] }` in their `[dev-dependencies]`.

**`crates/chicago-mcp` structure:**

```
crates/chicago-mcp/
  Cargo.toml           ← rmcp + rmcp-macros here and nowhere else
  src/
    lib.rs             ← re-exports; feature-gated modules
    harness/
      server.rs        ← McpServerHarness
      client.rs        ← McpStubServer
      session.rs       ← McpSession<S> state machine
    assert/
      mod.rs           ← assert_tool_input_valid, assert_content_array, McpErrorAssert
      schema.rs        ← assert_tool_schema_stable (insta)
    transport/
      pipe.rs          ← McpPipe (tokio duplex)
      child.rs         ← child-process transport wrapper over rmcp
    ocel/
      mod.rs           ← build_mcp_session_ocel, McpOcelEvent
    macros/            ← proc-macro re-exports from rmcp-macros + chicago-mcp-macros
  tests/
    fixtures/
      echo_mcp_server/ ← minimal hand-rolled MCP server binary for harness tests
```

**Cargo features on `chicago-mcp`:**

| Feature | Enables |
|---|---|
| `testing` (default-off) | `McpServerHarness`, `McpStubServer`, `McpPipe`, `McpErrorAssert` |
| `snapshot-testing` | `assert_tool_schema_stable` via `insta` |
| `property-testing` | JSON-RPC codec `proptest` roundtrips |
| `ocel` | OCEL 2.0 event builders |
| `macros` | re-exports `rmcp-macros` + any chicago-mcp proc-macros |

## Goals

- New isolated crate `crates/chicago-mcp` is the single home for `rmcp`; zero leakage to the rest of the workspace.
- `McpServerHarness`: spawn any MCP stdio server binary, drive it with typed requests, assert on typed responses — analogous to what `trycmd` does for CLI binaries.
- `McpStubServer`: stub-server for testing MCP client code; records requests, injects canned responses.
- `McpSession<S>`: phantom-type state machine that makes illegal MCP message orderings a compile error.
- High-level macros (`#[mcp_tool_test]`, `assert_mcp_tools!`, etc.) that collapse common test patterns to one line.
- Property-based tests for the JSON-RPC 2.0 message codec (roundtrip stability, discriminant safety).
- Snapshot tests for `tools/list` / `prompts/list` so schema drift is caught at review time.
- Full error-code coverage: every MCP and JSON-RPC 2.0 error code has a passing test.
- OCEL 2.0 integration: a test run produces a machine-verifiable evidence log.
- All of the above works against `~/osx-clnr`'s `oclnr-mcp` binary as the reference server.

---

## Non-Goals

- No LLM integration of any kind.
- No SSE/HTTP transport harness (stdio only for v26.6.31).
- No MCP server *implementation* — only testing infrastructure.
- No changes to `crates/chicago-tdd-lsp`.
- No support for the MCP `sampling` capability.
- No publishing to crates.io until API stabilizes past v26.6.31.

### [CHIC-311] `McpPipe` — in-process stdio transport mock

**As a** test author targeting an MCP stdio server  
**I want** a pair of in-process `tokio` pipes that speak raw JSON-RPC 2.0 line framing  
**so that** I can drive an MCP server's stdin and read from its stdout without network or LLM.

**Acceptance Criteria:**
- [ ] `McpPipe` wraps `tokio::io::duplex` (or `rmcp`'s `transport-async-rw` feature) to produce a `(client_half, server_half)` pair.
- [ ] `McpPipe::send(msg: &ClientJsonRpcMessage) -> Result<(), McpTestError>` serializes and writes atomically.
- [ ] `McpPipe::recv_timeout(Duration) -> Result<ServerJsonRpcMessage, McpTestError>` returns `McpTestError::Timeout` on deadline.
- [ ] Uses `rmcp`'s canonical `ClientJsonRpcMessage` / `ServerJsonRpcMessage` types — no hand-rolled JSON-RPC structs.
- [ ] `McpTestError` is a `thiserror`-derived enum; no `unwrap`/`expect` in module.
- [ ] Doctests cover: send+recv roundtrip, timeout fires, malformed JSON → `McpTestError::ParseError`.
- [ ] Gated behind `#[cfg(feature = "testing")]`.

**Notes:** `rmcp`'s `transport-async-rw` feature provides `AsyncReadWrite`-based transports. Use `tokio::io::duplex` to create the pipe pair and wrap each half with `rmcp`'s `AsyncReadWriteTransport`. This avoids re-implementing framing. Model timeout pattern after `tests/common/mod.rs` `docker_available()` — thread+channel, not `tokio::time::sleep`.

### [CHIC-312] `McpServerHarness` — process-level server test driver

**As a** developer who has written an MCP server binary  
**I want** a `McpServerHarness` that spawns the binary, performs the initialization handshake, and exposes typed request/response helpers  
**so that** I can write table-driven tests against my server without any manual stdio wrangling.

**Acceptance Criteria:**
- [ ] `McpServerHarness::spawn(cmd: impl Into<std::process::Command>) -> Result<Self, McpTestError>` starts the binary with stdin/stdout piped; uses `rmcp`'s `transport-child-process` feature internally.
- [ ] `harness.initialize() -> Result<InitializeResult, McpTestError>` performs the full MCP handshake (sends `initialize`, receives result, sends `notifications/initialized`).
- [ ] `harness.tools_list() -> Result<Vec<Tool>, McpTestError>` — typed via `rmcp`'s `Tool` type.
- [ ] `harness.call_tool(name, args: serde_json::Value) -> Result<CallToolResult, McpTestError>`.
- [ ] `harness.shutdown()` sends `shutdown`, waits for exit-0, panics on non-zero (test failure).
- [ ] Request IDs are monotonically incrementing `u64`s managed internally.
- [ ] Timeout per request defaults to 5 s, overridable via `McpServerHarnessBuilder`.
- [ ] Integration test in `crates/chicago-mcp/tests/server_harness_tests.rs` exercises a minimal echo fixture server through the full lifecycle.
- [ ] Gated behind `#[cfg(feature = "testing")]`.

**Notes:** `rmcp`'s `transport-child-process` (`TokioChildProcess`) is the direct transport primitive — no need to hand-roll process stdin/stdout piping. The echo fixture `crates/chicago-mcp/tests/fixtures/echo_mcp_server/main.rs` should be a minimal server built with `rmcp`'s `server` feature so it exercises real codec compatibility. Use the `star_toml_e2e.rs` `Once::call_once` pattern to compile the fixture binary once per test run.

**As a** developer who has written MCP client code

### [CHIC-314] Tool call round-trip assertions

**As a** test author  
**I want** typed assertion helpers that validate the full `tools/call` round-trip: input schema conformance, content-array shape, and `isError` semantics  
**so that** schema drift between a tool's declared `inputSchema` and its actual runtime behavior is caught in CI.

**Acceptance Criteria:**
- [ ] `assert_tool_input_valid(tool: &Tool, args: &serde_json::Value) -> Result<(), McpTestError>` validates against `tool.input_schema` using `jsonschema` crate (optional dep under `testing` feature).
- [ ] `assert_content_array(result: &CallToolResult)` checks: non-empty; each item has a valid `type`; `text` items have non-empty `text`; `image` items have `data` + `mimeType`; `isError: false` items contain no error messages.
- [ ] `assert_tool_schema_stable(harness, tool_name)` fetches `tools/list`, extracts the named tool, canonicalizes `inputSchema` (via `BTreeMap` deserialization), and calls `insta::assert_json_snapshot!`.
- [ ] Acceptance criteria encoded as doctests in `src/assert/schema.rs`.
- [ ] Gated behind `#[cfg(feature = "testing")]`; `snapshot-testing` feature additionally required for `assert_tool_schema_stable`.

**Notes:** `jsonschema = { version = "0.29", optional = true }` (pure Rust, no C FFI). Snapshots stored under `crates/chicago-mcp/tests/snapshots/`. Canonicalize by deserializing to `serde_json::Value`, converting to `BTreeMap<String, Value>` recursively, re-serializing — keys sort automatically.

### [CHIC-315] `McpSession<S>` — phantom-type lifecycle state machine

**As a** test author  
**I want** a typed state machine that enforces legal MCP message orderings at compile time  
**so that** calling `tools/call` before `initialize` is a compile error, not a confusing runtime panic.

**Acceptance Criteria:**
- [ ] Zero-sized marker types: `Uninitialized`, `Ready`, `ShutdownRequested`, `Closed`.
- [ ] `McpSession<S>` wraps `McpServerHarness`; generic over state marker.
- [ ] `McpSession::new(harness) -> McpSession<Uninitialized>`.
- [ ] `fn initialize(self) -> Result<McpSession<Ready>, McpTestError>` — `impl McpSession<Uninitialized>` only.
- [ ] `fn tools_list(...)` and `fn call_tool(...)` — `impl McpSession<Ready>` only.
- [ ] `fn shutdown(self) -> McpSession<Closed>` — `impl McpSession<Ready>` only.
- [ ] Compile-fail test (`trybuild`) proves `session.call_tool(...)` on `McpSession<Uninitialized>` does not compile.
- [ ] Integration test: `Uninitialized → Ready → Closed` against `oclnr-mcp` binary.
- [ ] Gated behind `#[cfg(feature = "testing")]`.

**Notes:** Direct model is the existing phantom-type AAA Poka-Yoke in `src/core/` — same `PhantomData<S>` pattern. `trybuild` as `[dev-dependency]` only. The `oclnr-mcp` binary path can be resolved via `env!("CARGO_BIN_EXE_oclnr-mcp")` if chicago-mcp is added as a dev-dep in osx-clnr; otherwise pass the path via env var in the test.

### [CHIC-316] High-level macros for reducing MCP test boilerplate

**As a** developer writing MCP server tests  
**I want** proc-macros and declarative macros that collapse common test patterns to a single attribute or assertion  
**so that** I can add new tool tests without copy-pasting harness setup and teardown.

**Acceptance Criteria:**
- [ ] `#[mcp_server_test(bin = "oclnr-mcp")]` proc-macro attribute: injects `McpSession` setup/teardown around the test body; the test function receives `session: McpSession<Ready>` as its first argument.
- [ ] `assert_mcp_tools!(session, ["audit_scan", "plan_build", "delete_run"])` declarative macro: fetches `tools/list` and asserts the named tools are all present; fails with a diff listing missing/unexpected tools.
- [ ] `assert_mcp_tool_call!(session, "tool_name", {key: val, ...}, |result| { ... })` declarative macro: constructs args from a JSON literal, calls the tool, passes result to a closure for assertions.
- [ ] `mcp_error_test!(session, method, params, expected_code)` declarative macro: sends an arbitrary JSON-RPC call and asserts the response error code.
- [ ] All macros are re-exported from `chicago-mcp` root under `#[cfg(feature = "macros")]`.
- [ ] `rmcp-macros` re-exports (e.g., `#[tool]`, `#[server]`) are also re-exported under the same feature flag.
- [ ] Each macro has at least one doctest demonstrating its use against the echo fixture server.
- [ ] Gated behind `#[cfg(feature = "macros")]`.

**Notes:** `#[mcp_server_test]` is a proc-macro in `crates/chicago-mcp/src/macros/` (or a companion `chicago-mcp-macros` crate if proc-macro isolation is needed). Declarative macros live in `src/macros/mod.rs` under `macro_rules!`. The `rmcp-macros` crate (`#[tool]`, `#[server]` attributes for server implementation) should be re-exported here so osx-clnr-style implementors only need one dep.

### [CHIC-317] Property-based tests for JSON-RPC 2.0 message codec

**As a** framework maintainer  
**I want** `proptest`-driven roundtrip and discriminant-stability tests for every JSON-RPC 2.0 message type  
**so that** codec bugs are found by the fuzzer rather than in production.

**Acceptance Criteria:**
- [ ] `rmcp`'s `ClientJsonRpcMessage` and `ServerJsonRpcMessage` (or their constituent types) have `proptest::arbitrary::Arbitrary` impls — either via `proptest-derive` or manually in `tests/mcp_codec_tests.rs`.
- [ ] Roundtrip property: `serialize(msg) |> deserialize |> serialize` produces identical bytes.
- [ ] Discriminant property: a response with `result` must never deserialize as an error response.
- [ ] ID property: fractional number IDs (`1.5`) are rejected.
- [ ] Params-null property: omitting `params` and `params: null` deserialize identically.
- [ ] Tests in `crates/chicago-mcp/tests/codec_tests.rs`, gated behind `property-testing` feature.
- [ ] Runs under 30 s in `nextest` default profile.

**Notes:** `proptest` is already an optional dep in the root workspace. Add it as optional to `chicago-mcp`'s `Cargo.toml` under `property-testing` feature. Mutation pattern from `blake3_receipt_tests.rs`: generate valid message → corrupt discriminant field → assert deserialization fails or returns wrong variant.

**As a** framework user who needs an auditable evidence trail  
**I want** `McpServerHarness` operations to emit OCEL 2.0 events  
**so that** a test run produces a machine-verifiable process log consistent with the rest of the chicago-tdd-tools evidence pipeline.

Params digest: `blake3` over canonical JSON of `rmcp`'s params value — not raw bytes, since params may contain secrets.

## Resolved Decisions

| Question | Decision |
|---|---|
| JSON-RPC types crate | Use `rmcp 2.0.0` canonical types; no hand-rolled structs |
| `rmcp` dep isolation | Contained entirely in `crates/chicago-mcp`; opt-in as `[dev-dependencies]` |
| Fixture server | Built with `rmcp`'s `server` feature; lives in `crates/chicago-mcp/tests/fixtures/echo_mcp_server/` |
| `jsonschema` acceptability | Add as optional dep under `testing` feature; verify compile time before CHIC-314 |
| SSE transport | Out of scope for v26.6.31; design `McpPipe` with a transport trait from the start |
| Macro layer | Proc-macros + declarative macros in `chicago-mcp`; re-export `rmcp-macros` so implementors have one dep |

## Open Questions

1. **`chicago-mcp-macros` sub-crate vs inline:** Proc-macros must live in their own crate (`proc-macro = true`). Should this be `crates/chicago-mcp-macros/` as a sibling, or should `chicago-mcp/src/macros/` delegate to an internal proc-macro crate? The sibling approach is cleaner for publishing; the internal approach is simpler for a monorepo. Decision needed before CHIC-316.

2. **`#[mcp_server_test]` binary resolution:** The macro needs the path to the server binary under test. Options: (a) `env!("CARGO_BIN_EXE_oclnr-mcp")` requires the test crate to declare a `[[bin]]` dep on the server; (b) an `OCLNR_MCP_BIN` env var set in `.cargo/config.toml`; (c) the macro accepts a `bin_path` argument resolved at test time. Which is least fragile across `cargo test` vs `cargo nextest`?

3. **`osx-clnr` as a test fixture:** Should `crates/chicago-mcp` carry a dev-dependency on `osx-clnr` (path dep) so integration tests can use `oclnr-mcp` directly, or should the fixture echo server be the only binary dependency? The path dep approach means `chicago-tdd-tools` and `osx-clnr` are coupled at test time.

## Acceptance Definition

The epic is complete when:

1. `cargo build -p chicago-mcp --all-features` passes; `cargo build` (default members) does not compile `rmcp`.
2. `cargo test -p chicago-mcp --features testing,snapshot-testing,property-testing,ocel,macros` passes all 8 story test suites.
3. An end-to-end test in `crates/chicago-mcp/tests/e2e_oclnr_mcp.rs` exercises `oclnr-mcp` through `McpSession`: `Uninitialized → Ready` (initialize + tools/list + assert_mcp_tools!) `→ Closed` (shutdown) and produces a valid OCEL log.
4. All five MCP error codes have passing tests in `error_tests.rs`.
5. Snapshots `snapshot_tests__tools_list.snap` and `snapshot_tests__prompts_list.snap` are committed.
6. `clippy -D warnings` (all groups) clean across `chicago-mcp`.
7. No `unwrap`, `expect`, `panic!`, `todo!`, `unimplemented!` in non-test `chicago-mcp` source.
8. Root `CLAUDE.md` updated: `rmcp` constraint documented.
